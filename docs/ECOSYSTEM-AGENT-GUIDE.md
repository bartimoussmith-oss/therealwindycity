## Status vocabulary
Track implementation, verification, deployment and follow-up independently. Implemented is not tested; tested is not deployed; deployed is not independently verified live.
- Completed: only a bounded acceptance criterion with linked evidence, exact input/output revision and test results.
- Needs finishing: missing behavior or integration with clear acceptance criteria.
- Needs troubleshooting: a reproducible failure or unavailable required result; preserve uncertainty about the cause.
- Needs optimization: functioning behavior with a measured baseline and a proposed improvement. Do not label something slow without measurement.
- Unverified: insufficient inspection or stale evidence; not synonymous with broken.
A project may have several work flags. Do not replace missing evidence with completion percentages.

## Agent claim and handoff
Before editing: read instructions in each target repo, inspect current main and task PRs, obtain the designated coordinator's acknowledgement, reserve non-overlapping paths, and record the input SHAs. This document creates no automatic lock.
Handoff fields: task_id, agent_id, owner approval, target repo/branch, base SHA, claimed paths, dependencies, inputs and hashes, changed paths, output commit/PR, exact commands/results, stage counts, reproduced failures, privacy review, exclusions, next action. Use coordination/handoffs in the existing integration workspace where that plan applies; do not publish private source material in handoffs.
Do not merge other agents' PRs just because titles overlap. Ask the coordinator to resolve ownership and schema conflicts. Do not force-push, rewrite source history or commit credentials. Follow host/tool approval requirements for writes, secrets, paid resources and deployments.

## Completion and release gates
Require reviewed diff, applicable tests on the candidate revision, independent provenance/privacy checks where applicable, internal/base-path link checks and explicit release approval. After publication, check public bytes/revision and working downloads; HTTP success alone does not prove correct content. Record browser interaction testing separately from syntax/static tests. If unable to verify a core condition, report blocked/unverified, not complete.

## Registry maintenance
A designated coordinator updates the public registry after evidence review. Every status change needs date, scope and supporting link or revision. Keep older evidence in history rather than silently erasing it. Check timestamps should be compared to the agent's actual clock; they are not auto-refreshed. Private projects are represented publicly only as an access-controlled workstream count/summary after approval, not names or private links.
